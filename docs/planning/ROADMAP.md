# IdeaOS-Agent 开发路线图

## 路线原则

v0.1 的唯一目的，是验证一个假设：

**AI 能否帮一个模糊想法，长出一条可执行的路径，并让用户产生「原来下一步该这样做」的感觉。**

这个假设在当前阶段已经得到初步验证，因此从 v0.2 开始，路线图切换为**版本优先**视角：

- `v0.1` 负责验证单次分析价值与交互模型主线
- `v0.2` 负责把单次分析沉淀为可回看的长期资产
- 后续版本再评估更强的项目空间、编辑能力与外部信息源

------

## v0.1 总结

当前 `main` 已经代表 `v0.1` 的稳定主线，核心成果包括：

- 跑通端到端的单次分析链路
- 建立假设透明化与单轮澄清的交互模型
- 提供最小可运行 Web 界面
- 完成测试、类型检查、环境约定与换行治理等工程收口

v0.1 的定位仍然不变：

- 它是一个**单次分析产品**
- 它强调**显式澄清而非自由陪聊**
- 它不做自动跨会话记忆

------

## v0.2 主题：Session Archive / Feishu Archive

### 目标

v0.2 的主题不是“更强聊天”，而是“**把一次有效分析沉淀为可回看的资产**”。

它要解决的核心问题是：

- 分析结果刷新后即消失，难以长期积累
- 用户无法自然回看某次想法的完整澄清与分析上下文
- 缺少从“单次分析”走向“想法资产沉淀”的最小桥梁

因此 v0.2 的主目标是：

1. 为每次**完成态分析**生成结构化会话记录
2. 使用本地 `SQLite` 保存最小索引与归档状态
3. 自动创建一份飞书文档作为面向人的归档载体
4. 将归档链接返回给前端，方便用户立即打开

### 核心决策

- **仅在完成态归档**：只有当 `needs_clarification=false` 且返回完整分析时，才触发正式归档
- **一条完整会话 = 一份飞书文档**：一次原始输入 + 可选单轮澄清 + 最终分析，共享一个 `session_id`
- **本地索引 + 飞书文档双层结构**：`SQLite` 负责机器可追踪状态，飞书负责人类可阅读结果
- **归档失败不阻塞主链路**：分析成功后即使飞书写入失败，也不回滚主分析结果
- **无自动跨会话记忆**：历史记录默认不自动注入后续分析链路，用户可显式回看，但不做后台自动脑补

### 最小范围

v0.2 的最小实现只覆盖以下能力：

- `SessionRecord` / `ArchiveRecord` 数据结构
- 本地 `SQLite` 索引存储
- 飞书归档适配层
- 分析成功后的自动归档触发
- 前端展示 `archive_status` 与 `archive_url`

### 明确不做

以下内容不进入 v0.2 的最小范围：

- 自动把历史记录注入下一轮分析，形成默认长期记忆
- 多轮自由聊天或多会话上下文拼接
- 飞书双向编辑回写
- 多 Agent、向量数据库、工作流编排
- 完整用户项目空间或多人协作系统

### 里程碑建议

建议将 v0.2 拆为以下四个里程碑：

1. `M1`：会话记录模型与归档契约
2. `M2`：本地 `SQLite` 索引存储
3. `M3`：飞书自动归档适配
4. `M4`：前端归档状态与文档链接体验

### 成功标准

如果 v0.2 达成以下条件，则认为目标成立：

- 用户完成一次正式分析后，能立即拿到飞书文档链接
- 系统能在本地 `SQLite` 中查询到该次会话索引与归档状态
- 飞书归档失败时，主分析结果仍能正常返回
- 产品边界仍然保持“无自动跨会话记忆”

------

## v0.2.5 主题：Archive Follow-up / Plan Refinement

### 目标

`v0.2.5` 的目标不是把产品改造成“长期记忆聊天助手”，而是在 `v0.2.0` 的归档基础上，补上一个最小但自然的动作：

**基于某次已完成归档的方案，继续追问、局部完善，并在用户确认后生成新版完整方案。**

它要解决的问题是：

- `v0.2.0` 的归档已经能回看，但还不能自然地“沿着某次结果继续推进”
- 用户想改某一部分时，只能重新发起一轮原始分析，成本高且不够贴合上下文
- 原方案与后续修改之间缺少稳定的父子关系

### 核心交互

建议的最小交互为：

1. 用户基于某个已归档 session 发起 follow-up
2. 系统默认返回“局部完善结果”
3. 用户确认修改后，再生成一版“新版完整方案”
4. 新结果创建新的 `session_id`，并继续归档

### 核心决策

- **一轮 follow-up = 一个新 session**：不覆盖原始分析结果
- **允许连续 follow-up**：理论上可以 `A -> B -> C` 持续推进，但每一步都必须显式基于某个父 session
- **仍然单次有界**：每次 follow-up 默认直答，最多一次澄清
- **完整方案首版优先程序合成**：被修改板块更新，未修改板块原样继承
- **飞书先做逻辑父子关系**：follow-up 先归档为新文档，在正文中保留父 session 与父文档链接

### 最小范围

`v0.2.5` 首版只覆盖以下能力：

- follow-up 输入与局部完善结果
- `parent_session_id` 等最小父子关系
- 本地结构化会话快照存储
- 用户确认后生成新版完整方案
- follow-up 结果的再次归档

### 明确不做

以下内容不进入 `v0.2.5` 最小范围：

- 多轮自由聊天
- 自动读取全部历史再推理
- 历史记录列表与筛选
- 可视化线程树或项目空间
- 飞书文档双向回写
- 真实 Feishu 树状父子结构的完整管理

------

## v0.3 主题：Idea Thread / History Navigation（已完成）

基于 `v0.2.5` 的 follow-up 闭环，`v0.3.0` 已完成历史记录与 idea thread 的首版能力收口：

### 目标

`v0.3.0` 解决的是“如何查看与管理一条想法的演进链路”。

它更适合承接以下问题：

- 历史记录列表与筛选
- 显式“从某次历史继续 follow-up”的入口
- 一个 idea 下多个 session 的线程关系
- 结果编辑、分享与项目空间
- 真实 Feishu 层级组织或 Wiki node 管理
- Similar Project Finder 接入外部信息源

这些方向仍然要遵守一个前提：

**先把“显式 follow-up”做稳定，再决定是否让历史真正形成可导航的 idea thread。**

### 核心原则

- 历史记录首先服务“回看与继续完善”，而不是变成自动长期记忆
- 历史导航必须是显式操作，不做 silent prompt 注入
- 线程结构先在本地 `SQLite` 与 API 层跑通，再评估是否同步映射到真实 Feishu 层级

### v0.3.0 交付范围

`v0.3.0` 最终收敛为“历史可见、线程可继续、边界仍受控”的版本，而不是一步做成完整项目空间。

1. `M1`：线程标识与存储补强
   - 为同一条想法链路补充稳定的线程聚合键，例如 `root_session_id` 或 `thread_id`
   - 明确 `analysis / follow_up_refinement / full_plan_composed` 在历史链中的展示语义
   - 保持现有 `session_id / parent_session_id` 不变，在其上补线程视角，而不是推倒重来
2. `M2`：历史查询 API
   - 新增本地历史列表与详情查询接口
   - 支持按时间倒序查看最近结果、按线程查看父子链路
   - 支持从任意已完成 session 显式发起下一轮 follow-up
3. `M3`：前端历史导航
   - 在 `/app` 中补最小历史记录列表，而不是立即做复杂工作台
   - 支持查看 session 类型、更新时间、归档状态、飞书链接
   - 支持“打开该结果”“基于该结果继续完善”“查看当前链路上下文”
4. `M4`：归档与线程协同增强
   - 在飞书文档正文中补更清晰的来源链路信息
   - 评估是否需要把父子文档关系进一步映射为 Feishu 子文档或 Wiki 结构
   - 继续保持飞书文档不是唯一系统状态来源

### 当前版本状态

- `v0.2.5` 已完成收口并单独发布到 `release/v0.2.5`
- `v0.3.0` 已完成收口，发布分支为 `release/v0.3.0`
- `v0.3.0` 的具体实现步骤与收口状态统一维护在 `docs/planning/PROGRESS.md`

### v0.3.0 成功标准

- 用户可以在前端看到本地历史记录列表
- 用户可以明确选择任意已完成 session 作为下一轮 follow-up 的父节点
- 系统可以展示一条想法链路中的父子关系与当前归档状态
- 整个产品仍然不引入自动跨会话长期记忆

## v0.4 主题：Frontend Interaction / Layout Refresh（已完成）

### 目标

`v0.4.0` 的优先级不再是补新的历史主能力，而是在不改变产品边界的前提下，提升当前前端交互布局与信息阅读体验。

它更适合承接以下问题：

- 当前 `/app` 虽然已经能完成分析、归档、follow-up 与历史导航，但整体布局仍偏粗糙
- 结果区、历史区、follow-up 区之间的信息层级还可以更清晰
- 按钮动作、状态反馈、加载提示与阅读节奏仍有进一步打磨空间

### 核心原则

- 不因为前端改版而重做 `v0.3.0` 已稳定的后端分层与数据契约
- 优先优化信息层级、交互节奏与可读性，而不是引入复杂工作台
- 仍保持“显式历史导航，不等于自动长期记忆”的产品边界

### 当前状态

- `v0.4.0` 已完成发布收口，发布分支为 `release/v0.4.0`
- `v0.4.0` 已完成前端三段式壳层、空状态与结果态重排、左侧历史导航收敛、工作区链路面板、统一 loading / 错误反馈与响应式收口
- `v0.4.0` 的具体执行步骤、验收清单与收口状态统一维护在 `docs/planning/PROGRESS.md`

------

## v0.4.5 主题：Frontend Polish / Engineering Debt Cleanup（进行中）

### 目标

`v0.4.5` 不是新的产品扩张版本，而是在 `v0.4.0` 已发布底座上继续做增量收口。

当前阶段聚焦三件事：

- 继续打磨现有 `/app` 的前端交互细节，而不是重做产品结构
- 收掉已经暴露出来的工程债，优先修正文档、版本元数据与依赖配置的不一致
- 在不突破产品边界的前提下，受控补上本地历史搜索、non-root leaf delete 与线性分支 follow-up 语义

### 核心原则

- 保持产品边界不变：单次分析主链路、最多一次澄清、显式 follow-up、显式历史导航、Feishu 归档、SQLite 状态来源之一
- 不引入真实外部搜索、真实登录、自动记忆、多 Agent 或新的后端平台能力
- 不借工程债清理顺手扩大 history / delete / draft / archive 语义
- 所有改动继续遵守 `api / application / domain / infrastructure / presentation / prompts` 分层

### 当前已确认优先项

1. 修正已发布 `v0.4.0` 与包元数据仍停留在 `0.2.0` 的不一致
2. 核实并处理 `pyproject.toml` 中可疑的 dev 依赖残留 `httpx2`
3. 在此基础上继续推进低风险前端交互细节优化
4. 以“本地 formal history 搜索、non-root leaf delete、全局版本号递增 + 轻关系标记”的约束推进下一轮 history 能力补全

### 当前状态

- `v0.4.5` 已启动，当前稳定基线仍为 `release/v0.4.0`
- `v0.4.5` 的 `P1/P2/P3` 已完成首轮实现与验证：本地 formal history 搜索、线性分支 follow-up 语义、non-root formal leaf delete 已接线完成
- `v0.4.5` 已完成 `P4` 收口：文档、测试、类型检查与分支整理已对齐，当前本地收口分支为 `release/v0.4.5`
- `v0.4.5` 的步骤化执行计划统一维护在 `docs/planning/PROGRESS.md`
