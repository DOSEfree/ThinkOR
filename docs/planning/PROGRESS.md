## 当前阶段判断

`v0.3.0` 已经完成分析、归档、follow-up、历史记录与 idea thread 的主链路闭环，当前最突出的问题不再是“缺少后端能力”，而是：

- `/app` 已能完成完整交互，但整体布局仍偏粗糙
- 历史列表、当前链路、输入区、结果区同时平铺，阅读节奏还不够清晰
- 空状态与结果态没有形成明显区分，首页聚焦感不足
- 按钮状态、加载反馈、占位信息与视觉层级仍有继续打磨空间

因此，`v0.4.0` 的任务不是扩新业务边界，而是把现有能力整理成一版更稳定、更清晰、更接近正式产品形态的前端界面。

------

## v0.4.0 目标

- 将当前 `/app` 重构为更明确的 `Topbar + Sidebar + Workspace` 三段式结构
- 让空状态更聚焦输入，让进入分析后的工作区更适合阅读和继续操作
- 将历史记录固定收敛到左侧导航区，避免继续与主结果区并排抢层级
- 保持 `CURRENT THREAD / 当前链路` 为显式上下文，但改为工作区内的上下文面板，而不是继续做双列表平铺
- 统一分析、澄清、follow-up、归档状态、错误与加载反馈的视觉表达
- 为未来登录、用户名展示、历史搜索预留 UI 位置，但本版不引入对应后端能力

## v0.4.0 核心设计冻结

### 信息架构

页面结构冻结为三层：

1. `Topbar`
   - 左侧：`IdeaOS` 品牌 logo
   - 右侧：用户名占位、用户头像、更多操作占位
2. `Sidebar`
   - 历史记录标题区
   - 搜索占位入口
   - 收起/展开入口
   - 最近 session 列表
3. `Workspace`
   - 空状态输入台
   - 分析中/分析后工作区
   - 历史详情查看
   - 当前链路上下文面板

### 搜索与登录边界

- 搜索先只做 UI 占位，不调用新接口
- 登录先只做展示位，不引入真实鉴权流程
- 这两个入口必须从视觉上看起来“已预留位置”，但不能误导用户以为功能已上线

### 当前链路位置

- 首版不继续做“左侧 recent sessions + 右侧 current thread”双历史栏
- 当用户打开某个历史结果或当前结果时，在工作区中显示 `CURRENT THREAD / 当前链路` 面板
- 该面板优先做成“默认简洁、按需展开”的上下文区，而不是长期占据大面积版面

### 交互状态原则

- 空状态和结果态必须明显区分
- 所有按钮沿用双语风格
- 加载反馈采用“两层反馈”：
  - 触发按钮本身进入 loading 态
  - 工作区同步进入统一 busy 态

## 当前执行顺序

为避免 `v0.4.0` 在前端改版过程中滑向“借机重做产品逻辑”，执行顺序固定如下：

1. `M1`：先改页面壳层、设计变量与静态资源目录
2. `M2`：再改空状态与输入工作区
3. `M3`：然后重排历史导航与当前链路位置
4. `M4`：最后统一结果阅读体验、加载反馈与响应式收口

每一步都必须满足以下约束：

- 不新增搜索后端逻辑
- 不新增登录后端逻辑
- 不改现有分析、归档、history、follow-up 的 API 语义
- 不把历史导航做成自动长期记忆入口
- 不为了视觉整洁而提前做与 `v0.4.0` 无关的大重构
- 新增交互、样式和资源迁移必须同步更新文档与变更记录
