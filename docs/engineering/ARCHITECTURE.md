# 系统架构

## 架构目标

当前稳定版本沿用 Python 主体路线，优先保证以下几点：

- 简单
- 可维护
- 可解释
- 便于与 Agent 协作开发

------

## 总体方案

当前采用单仓库、Python 主体、轻量 Web 展示的结构。

核心分层如下：

1. `presentation`：页面展示与接口入口
2. `application`：编排分析流程
3. `domain`：核心数据结构与业务规则
4. `infrastructure`：模型调用、外部 API、文件与存储适配

------

## 建议目录

```text
src/ideaos_agent/
├─ api/
├─ application/
├─ domain/
├─ infrastructure/
├─ prompts/
└─ models.py
```

说明：

- `prompts/` 单独存放提示词模板，避免和业务代码耦合
- `models.py` 作为初始化阶段的核心数据模型入口，后续可以逐步拆分
- `main.py` 提供最小 FastAPI 应用入口，保证项目在 Phase 0 就可本地启动

------

## 请求流

一条典型请求链路如下：

1. 用户提交一个原始想法
2. 接口层完成输入校验
3. 应用层组织分析流程
4. 基础设施层调用模型或检索服务
5. 领域层组装统一输出结构
6. 展示层返回页面或 JSON 结果

------

## 当前阶段暂不引入

为避免过度设计，以下能力当前仍不引入：

- 多 Agent 编排
- 长期记忆
- 向量数据库
- 工作流引擎
- 分布式任务系统
- 微服务拆分

------

## 输出对象原则

所有模块输出都应尽量结构化，便于：

- 页面展示
- JSON 返回
- 后续导出为 PDF
- 持续测试
- 后续版本演进

------

## 未来扩展边界

后续如果进入 `v0.3+`，可以再评估：

- 历史记录存储
- 用户项目空间
- 更丰富的结果编辑能力
- 外部信息源接入

但这些都不应反向影响当前轻量分层架构的简洁性。

------

## v0.2 收口备注

当前已落地的 v0.2 方向为“Session Archive / Feishu Archive”，工程上保持以下边界：

- `application`：在正式分析完成后编排归档动作，但不把飞书写入逻辑混入主分析服务
- `domain`：定义会话记录、归档状态与最小索引字段
- `infrastructure`：分别承接本地 `SQLite` 索引存储与飞书归档适配
- `presentation`：展示归档状态与文档链接，而不是直接承担持久化职责

额外约束：

- 归档失败不得回滚主分析结果
- 本地 `SQLite` 索引与飞书文档各司其职，不将飞书当作唯一系统状态来源
- 历史记录默认仅用于归档与回看，不自动参与后续推理
