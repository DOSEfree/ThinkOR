# GitHub 协作流程

## 目标

在不引入沉重流程负担的前提下，让项目具备实际开发级别的协作秩序。

------

## 分支策略

当前建议使用以下分支命名：

- `main`：稳定主分支
- `feat/...`：功能开发
- `docs/...`：文档调整
- `fix/...`：缺陷修复
- `chore/...`：工程与维护工作

------

## Issue 分类

建议至少维护以下 Issue 类型：

- `feature`
- `docs`
- `bug`
- `chore`

Issue 里应尽量写清楚：

- 背景
- 目标
- 非目标
- 验收标准

------

## Pull Request 原则

每个 PR 应尽量做到：

- 范围单一
- 变更可解释
- 附带必要文档更新
- 附带测试结果或说明

------

## 版本日志

所有重要变更统一记录到根目录 `CHANGELOG.md`。

建议规则：

- 开发中内容先写入 `Unreleased`
- 发布时再归档到具体版本
- 版本描述优先写“对项目有何影响”

------

## 里程碑建议

建议至少设置以下里程碑：

1. `v0.1-init`
2. `v0.1-core-analysis`
3. `v0.1-release`

------

## GitHub Project 建议字段

如果你使用 GitHub Projects，建议字段尽量简单：

- Status
- Priority
- Type
- Milestone

------

## 当前维护建议

当当前功能分支已经足以代表阶段性稳定状态时，建议进行以下操作：

1. 将工程与文档收口改动整理为单一主题提交
2. 通过 Pull Request 将阶段性稳定分支合并回 `main`
3. 让 `main` 始终代表当前稳定主线
4. 基于新的 `main` 再开启下一版本规划或功能分支

这样可以让远程仓库持续保持清晰历史，而不是让真实主线长期停留在 `feat/...` 分支。
